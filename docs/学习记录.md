## 2026-10-30 · 用 IDEA 终端启动后端

### 想搞清楚什么
在 IntelliJ IDEA 里，怎么不用点绿三角、纯靠终端把后端跑起来。

### 结论
入口只有 `jeecg-system-start` 模块，用 Maven 的 `spring-boot:run` 在 `jeecg-boot` 目录执行，**必须用 `-pl` 指定模块，且不要加 `-am`**。实测启动耗时 **10.8 秒**。

### 命令

```powershell
# IDEA 终端快捷键 Alt + F12（默认 PowerShell）
cd E:\Java\JeecgBoot\jeecg-boot
mvn -pl jeecg-module-system/jeecg-system-start spring-boot:run
```

停止：终端里按 `Ctrl + C`。

### 验证方式

日志出现这两行即成功：

```
Started JeecgSystemApplication in 10.837 seconds
Application Jeecg-Boot is running!
	Local: http://localhost:8080/jeecg-boot
```

再访问接口文档确认端口通：`http://localhost:8080/jeecg-boot/doc.html` → 200。

### 关键点（为什么这么写）

| 点 | 说明 |
| --- | --- |
| 工作目录 | 必须是 `E:\Java\JeecgBoot\jeecg-boot`，Maven 根 `pom.xml` 在这里；外层 `E:\Java\JeecgBoot` 是仓库根，没有后端 pom |
| `-pl` | 只有 `jeecg-system-start` 有 `JeecgSystemApplication` 主类；不加 `-pl` 会让所有模块都执行 run 目标而报错 |
| 不加 `-am` | `-am` 会把 `spring-boot:run` 连带跑到依赖模块上；能不加是因为各模块 jar 已 `install` 到本地仓库 `E:\Java\maven-repo` |
| 改了底层模块 | 改 `jeecg-boot-base-core`、`jeecg-system-biz` 等之后必须先 `mvn -pl <模块> -am clean install -DskipTests`，否则 `run` 用的还是旧 jar |
| profile | 不用写 `-P dev`：根 `pom.xml` 里 `dev` 是 `activeByDefault`，`application.yml` 的 `@profile.name@` 会被资源过滤替换成 `dev` |
| 改 yml 后 | 直接重跑命令即可生效，`spring-boot:run` 会先执行 `test-compile` 重新过滤资源，不用 install、不用打包 |

### 踩坑

1. **终端报 `mvn 不是内部或外部命令`** —— IDEA 终端没继承新配的环境变量。关掉 IDEA 重开，或用全路径：
   `& E:\Java\tools\apache-maven-3.9.9\bin\mvn.cmd -pl jeecg-module-system/jeecg-system-start spring-boot:run`
2. **日志中文全是乱码**（`��Ʒ������`）—— Jeecg 控制台按 GBK 输出、终端是 UTF-8 导致的显示问题，**不影响运行**。想看正常中文：终端先 `chcp 936`，或 Settings → Editor → File Encodings 三个都设 UTF-8。
3. **`Port 8080 was already in use`** —— 先找占用：
   ```powershell
   netstat -ano | findstr :8080
   taskkill /PID <查到的PID> /F
   ```
4. **绿三角启动报 `@profile.name@` 解析不了** —— 那是 IDEA 自己编译、不走 Maven 资源过滤。学习阶段统一用终端命令，行为最确定，日志也全在眼前。

### 备选启动方式

```powershell

# 2) 用现成脚本（内部是同一条 mvn 命令，已设好 JAVA_HOME/PATH）

mvn -pl jeecg-module-system/jeecg-system-start spring-boot:run -Dspring-boot.run.arguments=--server.port=8081
mvn -pl jeecg-module-system/jeecg-system-start spring-boot:run -Dspring-boot.run.profiles=prod
mvn -pl jeecg-module-system/jeecg-system-start spring-boot:run "-Dspring-boot.run.jvmArguments=-Xmx1g -Xms512m"
```

## 2026-11-02 · DSH 内置 IDE 模块：真机集成与三个「只在真机才炸」的坑

### 想搞清楚什么
把自研的 DSH IDE 插件（`packages/ide/` 下 10 个包：project-run、Remote 桥、补全三层、lsp 装配）装进真实 DSH profile 后，为什么 App 启动崩溃、`ide_run start` 静默失败、`ide_complete_llm` 返回空——以及这些坑的通用结论。

### 结论

- **崩溃根因**：插件客户端产物必须是 `window.__ModuleLoader__.load({ id, factory })` 闭包工厂（仓库 `clientBundle` 预设产出）。手写 tsdown 的普通 ESM 会让**所有**插件的合并客户端 bundle 语法解析失败（`Cannot use import statement outside a module`），App 直接弹「应用无法启动」。
- **Windows 命令坑**：`ctx.subprocess.spawn` 是 shell-free 的，而 `mvn`/`npm` 在 Windows 是 `.cmd` shim，直接 spawn 会立即退出且**无输出**（退出码 undefined）。正解：`cmd.exe /d /s /c <整行命令>`。
- **LLM 补全坑**：`deepseek-v4-pro` 默认推理档会把 512 的 `maxTokens` 全烧在思考 token 上，可见文本为空。正解：`ctx.llm.prepareCall` 的 configure 回调里选 `model.reasoning?.efforts[0]?.id`（最低档）——与官方 session-title 的实现一致。

### 命令 / 代码

```powershell
# 本地包 → tarball → 装进 profile（pnpm 12.16.1）
cd E:\Java\dsh-ide\packages\ide\ide-run
pnpm pack --pack-destination E:\Java\dsh-ide\releases
cd C:\Users\Administrator\.dsh\profiles\desktop
pnpm install --force

# 版本兼容闸豁免（0.2.2-alpha.2 的包跑在 dsh 0.2.1-rc.5 上）
dsh plugin --profile desktop allow-version @deepseek-ai/dsh-tool-lsp@0.2.2-alpha.2 --dsh-version 0.2.1-rc.5 --accept-risk

# 崩溃日志
C:\Users\Administrator\AppData\Roaming\@deepseek-ai\dsh-desktop\logs\crash-*-web-boot.log
```

```ts
// Windows 命令包装（ide-run-local）
const argv = process.platform === 'win32'
  ? ['cmd.exe', '/d', '/s', '/c', command]
  : command.split(/\s+/)
```

### 验证方式

- 工具表出现 `ide_run` / `ide_complete` / `ide_complete_llm`（本轮真机实测通过前两项）；
- `ide_run detect` 在 `E:\Java\JeecgBoot` 返回 `jeecg-boot-parent`(maven) + `jeecgboot-vue3`(npm) 及脚本清单；
- `ide_complete` 在 `YingZhiRenScoreController.java` 光标处返回 `YingZhiRenScore`/`YingZhiRenScoreController`；
- LSP 直连冒烟：tsls 6.0.2 对 `add(1,2)` 的 `textDocument/definition` 正确返回 `b.ts` 第 0 行 16-19 字符。

### 踩坑（按被发现顺序）

1. **tarball 里 package.json 带 UTF-8 BOM** → loader 的 `JSON.parse` 直接拒，报 `Unexpected token ''`。PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会加 BOM，必须用 `[IO.File]::WriteAllText(path, text, UTF8Encoding($false))`。
2. **插件必须声明 `dsh.bundle.patch`** 指向自带的 `cordis.patch.yml`，内容形如 `- insert: { id: "@scope/name", name: "@scope/name" }`；**`@` 开头的标量 YAML 必须加引号**，否则报 `bad indentation of a mapping entry`。
3. **纯库不能进 `dsh.profile.bundles`**（如 `dsh-ide-completion` 只是依赖）：loader 会尝试 import 它当插件，报 `failed to import`。
4. **desktop profile 由 Electron 独占管理**，`dsh --profile desktop --dump-config` 被拒；验证合成要用自建 profile（如 `ide-test`）+ `--dump-config`。
5. **「禁用第三方插件」按钮会重置 profile**：bundles 只剩 base+web-app、`cordis.patch.yml` 被简化——恢复时要手动补回 bundles 与配置项。
